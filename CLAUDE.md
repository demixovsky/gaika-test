# Руководство для разработчиков: бот поддержки «Гайка»

## Архитектура проекта

Приложение состоит из асинхронных компонентов, которые собираются в
`app/main.py`: обработчики aiogram вызывают сервис LLM, сервис LLM выполняет
инструменты, а слой базы данных и репозиторий FAQ отвечают за хранение данных.

Контекст конкретного запроса Telegram необходимо передавать явно. Запрещено
хранить текущего пользователя, идентификатор чата или контекст инструментов в
глобальных изменяемых переменных.

Назначение файлов:

- `config.py` — чтение и проверка переменных окружения;
- `database.py` — схема SQLite и операции с сообщениями и заявками;
- `faq.py` — разбор Markdown, индексация FAQ и поиск;
- `tools.py` — схемы инструментов и доверенный контекст их выполнения;
- `llm.py` — системный промпт и ограниченный цикл вызова инструментов;
- `bot.py` — обработчики Telegram и административная команда `/reply`;
- `logging_utils.py` — журнал приложения и журнал вызовов LLM в JSONL;
- `main.py` — инициализация зависимостей и запуск бота.

## Обязательные правила

- `data/faq.md` — единственный источник фактической информации об автосервисе.
  Нельзя придумывать или дублировать в коде цены, график, услуги, гарантии и
  другие правила компании.
- Нельзя передавать весь FAQ в промпт модели. Для получения фактов модель должна
  использовать `search_faq`.
- Нельзя доверять идентификаторам Telegram и контактным данным, переданным
  моделью. Значения `chat_id`, `telegram_user_id` и `contact` для базы данных
  всегда берутся из текущего `ToolExecutionContext`.
- Каждый фактический запрос к LLM должен создавать одну строку в журнале JSONL.
  Запрещено записывать в журналы секреты, полные промпты и полные ответы модели.
- Цикл вызова инструментов должен иметь ограничение по числу итераций. Для
  каждого вызова инструмента необходимо вернуть результат модели, включая
  случаи некорректных аргументов и неизвестных инструментов.
- Запрещено жёстко прописывать в коде токены, ключи API, идентификаторы чатов,
  название модели и адрес сервиса LLM.
- Повторное создание заявки в рамках одного цикла обработки сообщения не
  допускается.

## Изменение базы данных

Начальная схема создаётся идемпотентными выражениями
`CREATE ... IF NOT EXISTS`. Нельзя удалять или полностью пересоздавать таблицы
`messages` и `tickets`: они содержат постоянные пользовательские данные.

Все дальнейшие изменения схемы должны оформляться явными последовательными
миграциями. Полное перестроение только таблицы `faq_fts` при запуске является
ожидаемым и безопасным поведением.

Доступ к SQLite должен оставаться асинхронным через `aiosqlite`. Все значения в
SQL-запросах необходимо передавать параметрами. Для параллельной обработки
сообщений должны оставаться включёнными режим WAL и `busy_timeout`.

## Правила работы с LLM и инструментами

- Использовать совместимый с OpenAI Chat Completions API через `AsyncOpenAI`.
- Название модели брать только из `LLM_MODEL`.
- Сохранять сообщения пользователя до вызова LLM, а ответ ассистента — только
  после успешной отправки в Telegram.
- В постоянной истории хранить обычные сообщения пользователя и ассистента.
  Результаты инструментов можно использовать только внутри текущего цикла LLM.
- Контекст разных чатов не должен смешиваться. Сообщения одного чата необходимо
  обрабатывать последовательно.
- `create_ticket` всегда использует реальные идентификаторы из обновления
  Telegram, даже если модель передала другие значения.

## Стиль кода и обработка ошибок

- Целевая версия — Python 3.12.
- Для функций, методов и структур данных использовать аннотации типов.
- Предпочитать небольшие асинхронные функции с одной понятной обязанностью и
  явную передачу зависимостей.
- Ошибки транспорта, SQLite и внешнего API обрабатывать на границах подсистем.
- Пользователю нельзя показывать трассировку стека или внутренние сведения
  приложения.
- Подробности ошибок записываются только в обычный журнал приложения.
- При изменении парсера, поиска, инструментов, базы данных или цикла LLM нужно
  добавлять или обновлять соответствующие тесты.

## Команды разработки

Установка зависимостей для разработки и запуск тестов:

```bash
python -m venv .venv
python -m pip install -r requirements-dev.txt
python -m pytest
```

Проверка и запуск Docker Compose:

```bash
docker compose config
docker compose build
docker compose up -d
docker compose logs -f bot
```

Перед отправкой изменений необходимо убедиться, что тесты проходят, секреты не
попали в репозиторий, а `runtime/support.db` и `runtime/llm_calls.jsonl`
игнорируются Git.
